# Backend Integration Guide
## Automated Attendance Predictor — ML Pipeline Handoff
### Group Ref: KHSIP-2026-MG-0002

---

## What We (ML Team) Built

A 3-model pipeline that predicts attendance and detects anomalies:

- **Prophet** — forecasts group-level attendance trends (next 7 days)
- **XGBoost** — predicts individual absence risk (next 7 days per person)
- **Isolation Forest** — detects anomalous attendance patterns
- **Alert System** — combines all 3 models into actionable alerts
- **Adaptive Learning** — retrains models as new data comes in

---

## What We Need From the Database

### Only 4 columns. Nothing else.

| Column | Type | Description | Example |
|--------|------|-------------|---------|
| person_id | string | Unique identifier for each student/employee | "STU-0042" |
| date | date | The attendance record date (business days only) | "2026-04-10" |
| attendance_binary | integer | 1 = present, 0 = absent | 1 |
| is_exam_period | integer | 1 = exam period, 0 = normal day | 0 |

**is_exam_period** must be populated from the academic calendar. The backend should have the exam dates configured and auto-fill this field.

Everything else (rolling averages, trends, anomaly scores, risk levels) is computed by our ML scripts. Do NOT compute any features on the backend.

---

## API Endpoints the Backend Should Expose

### 1. GET /api/attendance/raw?person_id=XXX
Returns raw attendance records for one person (all history).
Used when admin looks up a specific person.

### 2. GET /api/attendance/raw/all
Returns raw attendance records for ALL persons.
Used for model retraining (weekly).

### 3. POST /api/alerts
Receives the alert report JSON from the ML pipeline and stores it.
The frontend reads alerts from this endpoint.

### 4. GET /api/alerts?level=CRITICAL
Returns stored alerts filtered by level.
Frontend uses this to populate the dashboard.

### 5. GET /api/alerts/person/{person_id}
Returns the alert for a specific person.
Used for individual lookup ("What's Raffay's status?").

## Files We Deliver

### Model Files (in /models/ directory)
| File | Size (approx) | What It Is |
|------|---------------|------------|
| prophet_model.pkl | ~2 MB | Trained Prophet model |
| xgboost_model.pkl | ~500 KB | Trained XGBoost model |
| isolation_forest_model.pkl | ~1 MB | Trained Isolation Forest + scaler |

These are loaded by the alert system to make predictions.

### Script Files
| File | Purpose | When It Runs |
|------|---------|--------------|
| feature_engineering.py | Transforms raw DB data into model features | Every prediction request |
| prophet_model.py | Group-level trend forecasting | On demand |
| xgboost_model.py | Individual risk prediction | On demand |
| isolation_forest_model.py | Anomaly detection | On demand |
| alert_system.py | Combines all models, generates alerts | Daily or on demand |
| adaptive_learning.py | Retrains models on new data | Weekly (cron job) |

### Output Files (generated by the pipeline)
| File | Purpose | Who Consumes It |
|------|---------|-----------------|
| alert_report.json | Full alert report for all persons | Backend → Frontend |
| prophet_report.json | Group trend forecast | Backend → Frontend |
| xgboost_report.json | Model performance metrics | Admin monitoring |
| isolation_forest_report.json | Anomaly detection results | Admin monitoring |
| retraining_logs/retraining_history.json | Model performance over time | Admin monitoring |

---

## How the Full System Works (Data Flow)

```
STEP 1: Database exports raw data (4 columns)
           ↓
STEP 2: feature_engineering.py computes all features
           ↓
STEP 3: alert_system.py loads 3 models and generates alerts
           ↓
STEP 4: alert_report.json is saved
           ↓
STEP 5: Backend reads alert_report.json → stores in DB → serves to frontend
           ↓
STEP 6: Frontend displays dashboard
```

## Retraining Schedule

The adaptive_learning.py script should run weekly via a cron job or scheduled task.

**Recommended schedule:**
- Weekly: Run adaptive_learning.py (retrains XGBoost + Isolation Forest)
- Every semester: Retrain Prophet manually (needs 6+ months of data)
- Daily: Run alert_system.py to refresh alerts

**Cron job example (every Sunday at 2 AM):**
```bash
0 2 * * 0 cd /path/to/project && python adaptive_learning.py
```

**Daily alert refresh (every day at 6 AM):**
```bash
0 6 * * * cd /path/to/project && python alert_system.py
```

**Before retraining:** The backend must export fresh raw_attendance_data.csv from the database.

## Thresholds (Adjustable)

These are in alert_system.py and can be tuned after deployment:

| Threshold | Current Value | What It Controls |
|-----------|--------------|-----------------|
| xgboost_high | 0.60 | Risk score for HIGH alert |
| xgboost_medium | 0.35 | Risk score for MEDIUM alert |
| anomaly_boost | 0.15 | Risk boost when anomaly detected |
| prophet_declining_boost | 0.05 | Risk boost when group trend declining |
| exam_absence_rate_threshold | 0.30 | Min exam absence rate to flag |
| predicted_absences_high | 4 | Predicted absences for HIGH alert |
